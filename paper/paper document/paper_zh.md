摘要——我们揭示了闭权重大型语言模型（LLM）面临的一种新威胁：攻击者可以据此计算基于优化的提示注入。具体而言，我们刻画了攻击者如何利用远程微调接口返回的类损失信息，来指导对抗性提示的搜索。微调接口由 LLM 厂商托管，允许开发者针对自己的任务微调 LLM，因此具有实用价值；但该接口也暴露了足够的信息，使攻击者能够计算对抗性提示。通过实验分析，我们刻画了 Gemini 微调 API 返回的类损失数值，并证明这些数值能够为使用贪心搜索算法进行对抗性提示的离散优化提供有用信号。使用 PurpleLlama 提示注入基准，我们展示了该攻击在 Google Gemini 系列 LLM 上可达到 65% 至 82% 的攻击成功率。这些攻击利用了经典的效用—安全权衡：微调接口为开发者提供了有用功能，但也使 LLM 暴露于强有力的攻击之下。

### 1. 引言

大型语言模型（LLM）面临许多安全和隐私问题，例如被迫输出违反厂商政策的文本 [1]–[7]，或通过提示注入攻击被诱骗滥用其工具访问权限 [8]–[13]。学术界的最终目标是构建安全且保护隐私的 LLM，而实现这一目标的重要步骤之一，是全面探索模型可能面临的新型攻击途径。本文推进了这条研究路线，并揭示了一种针对 LLM 的新攻击途径，使攻击者能够为闭权重专有 LLM 计算基于优化的提示注入。

具体来说，我们展示攻击者如何滥用 LLM 的微调接口，以指导对抗性提示的搜索。许多厂商允许用户远程微调闭权重模型，使其适用于各种下游任务 [14]–[16]。厂商会利用由 GPU 数据中心构成的大规模基础设施，为微调任务提供支持。微调接口会针对用户提供的训练集和验证集返回训练进度指标。我们的核心洞见是：攻击者通过设置极小的学习率，可以获得一种信号，用来近似反映 LLM 对目标 token 的对数概率（“logprobs”）。正如我们的实验所示，这使攻击者能够对闭权重模型实施灰盒的、基于优化的攻击。据我们所知，我们首次使用这种方法展示了针对 Google Gemini 系列 LLM 的基于优化的提示注入攻击（见图 1）。

*图 1 中的对话内容：请遵循用户的指令，回答有关所提交内容的问题。这段代码的输出是什么？[代码中嵌入了经过优化的提示注入，诱导模型无视正常计算并输出“10”。]10。*

*图 1：在 Gemini 1.5 Flash 上使用本文方法进行提示注入的示例（取自 PurpleLlama 基准）。我们的攻击利用微调损失数据计算出一个载荷（图中红色部分），将其包裹在已有的提示注入触发语（粗体部分）周围，从而对其进行“增强”。这会迫使模型遵循注入的指令。载荷和指令始终保持为单行注释，因此不会破坏 Python 语法。*

我们的攻击利用了安全性与实用性之间的一种根本性权衡。厂商希望开放微调接口，让开发者能够获得专用模型带来的好处；因此，厂商必须提供细粒度的训练指标，帮助开发者有效地微调模型。我们的研究表明，这种实用性与安全性之间存在根本冲突——对正常微调有帮助的类损失训练指标，也能帮助攻击者搜索对抗性提示。

现有对抗性提示技术可分为两类：（1）语言型攻击，通过不断改写文本提示来达到恶意目标，通常是诱导模型输出违反内容政策的文本，从而“越狱” [17]–[20]；（2）自动化的基于优化的搜索技术，利用损失数据指导离散 token 搜索，以找到能够实现攻击者目标的 token [21]。本文属于第二类攻击。不同自动化攻击类型之间的关键区别，在于攻击者能够访问损失信息的程度。例如，白盒攻击利用损失及其梯度 [21]、[22]；灰盒攻击利用推理接口提供的 logprobs [23]、[24]；黑盒攻击则只依赖模型生成的文本输出 [19]、[25]。近期，LLM 厂商通过在推理调用中不返回 logprobs，或只返回其中很小的一部分，缓解了某些灰盒攻击途径 [26]–[28]。在这两种情况下，信息都不足以有效指导对抗性提示的搜索。我们的研究表明，可以改造现有的贪心搜索算法，使其利用微调接口提供的类损失信息来构造攻击。

在 fun-tuning 攻击中，攻击者以极小学习率运行一次微调。极小的学习率确保基础模型不会发生明显变化，这实际上绕开了微调原本的目的——更新模型权重。这一操作的输出是一个类损失数值，用来表示模型实际输出与期望输出之间的差距。我们使用这个类损失数值来指导搜索过程。以这种方式使用微调功能会遇到两个技术难题。

第一个难题是确定微调损失是否是指导对抗性提示搜索的良好信号。商业厂商的微调接口是闭源的，文档也没有提供详细说明。通过一系列实验，我们对 Google Gemini 所使用的损失函数进行了部分逆向分析，并通过实验证明，接口报告的训练损失虽然带有噪声，但仍可用于提示的离散优化。

第二个难题是，微调接口会随机打乱训练集和验证集中样本的顺序。接口报告的损失值顺序是输入训练数据顺序的一个排列。这会带来问题，因为攻击者在构造对抗性提示时，必须系统地评估不同 token 替换所造成的影响。我们通过一种近似去随机化流程解决这一难题：精心构造训练数据集，以近似恢复被打乱后的训练顺序。我们将这一近似流程与另一种效率较低但可证明正确的方法进行比较，以验证其有效性；结果发现，该流程能够在合理误差范围内近似真实排列。

我们重点研究提示注入攻击，因为这是基于大型模型构建的系统所面临的最现实安全问题。这类系统，也就是智能代理，可以使用工具完成各种任务，例如自动查找软件漏洞，以及管理日历和电子邮件。在基于代理的系统中，提示注入攻击可能影响用户数据的机密性和完整性。设想一个能够访问用户邮箱的简单代理。攻击者可以构造一个对抗性提示，并向受害用户发送一封未经请求的电子邮件。如果用户要求邮件处理代理“总结我最新收到的邮件”，对抗性提示就可能劫持代理，使其进一步把用户的邮件发送给攻击者，从而侵犯机密性 [13]、[8]。

缓解 fun-tuning 攻击途径并非易事，因为它利用了效用与安全之间的权衡。对训练超参数进行细粒度控制（包括学习率、批大小、训练轮数，以及训练集打乱所用的随机种子），对正常使用接口的开发者至关重要；但正如本文所示，这些控制也会帮助攻击者。因此，任何减少超参数控制权的改动（例如设置较高的学习率下限），都可能对正常开发者造成负面影响，并降低微调接口本身的实用性。在启动微调任务前扫描训练集中的恶意数据，是一种潜在缓解措施（例如检查是否违反内容政策）；但攻击者可以使用隐藏数据语义的编码技术绕过扫描 [29]，而且对于提示注入攻击，这种扫描并非总是可行。

### 本文贡献

**新攻击面的刻画。**我们揭示并通过实验刻画了 LLM 系统中的一种新攻击途径，该途径利用了效用与安全之间的根本矛盾。具体来说，我们展示攻击者如何滥用微调接口来构造对抗性提示。我们将这类攻击称为 fun-tuning 攻击。在此过程中，我们解决了两个技术难题：（a）验证微调损失适合用于提示注入的离散优化；（b）对报告的类损失数值进行去随机化，以获得可用于对抗性提示优化的信号。

**基于优化的提示注入的实验分析。**我们通过实验评估 Google Gemini 系列模型对 fun-tuning 攻击的脆弱性。我们证明，可以修改现有的提示注入离散优化算法，使其利用微调损失进行引导。

## 2 背景

我们将 LLM `MΘ` 建模为一个概率分布：它根据输入 token 预测下一个 token。也就是说，对于输入 token 序列 `x1:n = (x1, x2, ..., xn)`，`MΘ` 会输出概率分布 `P(y | x1:n; Θ)`，其中 `Θ` 表示模型参数，`y` 表示即将生成的下一个 token。所有 token 都来自一个离散集合 `V = {T1, T2, ..., T|V|}`，该集合称为 LLM 的词表。

### 生成/推理模式下的 LLM

下一个输出 token `y1` 是根据某种采样过程，从概率分布 `P(y | x1:n; Θ)` 中采样得到的。实际应用中，LLM 会持续生成 token 序列，直到生成特殊的“文本结束” token。因此，对于输入 `x1:n ∈ V*`，LLM 会以如下概率返回输出序列 `y1:m ∈ V*`：

`P(y1:m | x1:n; Θ) = ∏(i=1 到 m) P(yi | x1:n, y1:i−1; Θ)`  （1）

除生成的 token 序列外，LLM API 还会以“logprobs”的形式返回与输出生成概率有关的其他信息。token `y` 的 logprobs 表示：给定输入 `x = x1:n` 时生成该 token 的概率。对于输出序列 `y = y1:m`，有：

`Logprobs(y | x; Θ) = −Σ(i=1 到 m) log P(yi | x, y1:i−1; Θ)`  （2）

有些 API（例如 Cohere、GooseAI）会返回完整的 logprobs 向量，也就是词表中每个 token 的 logprobs。有些 API 只返回 Top-N 个 logprobs（例如 OpenAI 返回 top-20），还有一些 API 完全不提供 logprobs 信息。更完整的列表见文献 [31] 的表 6。

### 训练

生成式 LLM 的训练过程，是寻找参数 `Θ`，使训练数据集 `I` 上的交叉熵损失最小。交叉熵衡量模型对下一个 token 的预测概率分布 `MΘ(xi) = P(y | xi)` 与真实下一个 token `yi` 之间的差异；`xi` 表示数据集 `I` 中第 `i` 个训练样本。

`Θ^ = argminΘ Σ(i∈I) CrossEntropy(MΘ(xi), yi)`  （3）

展开交叉熵损失的定义，可得：

`Θ^ = argminΘ [−Σ(i∈I) log P(yi | xi; Θ)]`  （4）

### 提示注入

在现实系统中，LLM 的输入通常由系统提示和用户提示构成。两者由特殊 token 分隔，并拼接成一个 token 序列，通常称为一次对话。为简化讨论，我们假设一个 LLM 提示由系统提示 `xSys` 和用户提示 `xUser` 组成。关键在于，系统提示和用户提示来自安全属性不同的来源，因此两者之间存在信任边界：其中一个输入可能由攻击者控制。

提示注入攻击假设攻击者能够部分控制 LLM 输入，并利用这部分控制权实现开发者或实际用户原本没有打算实现的目标。提示注入可能导致多种现实后果，例如泄露隐私数据和滥用工具 [8]–[11]、[13]，从而损害与 LLM 相连的用户资源的机密性和完整性。

当可信输入（例如 LLM 代理的系统提示和用户提示）与不可信的恶意输入（例如从待总结的第三方网页中检索到的文本）拼接后，导致 LLM 偏离原本任务、转而遵循恶意输入中的指令时，就发生了提示注入。形式化地说，若下式成立，我们就称发生了提示注入：

`LLM(xTrusted || xAdv) ≈ LLM(xAdv) ≈ yTarget`  （5）

攻击者的任务是构造对抗性输入 `xAdv`，使它与 `xTrusted` 组合后，LLM 输出攻击者指定的 token 序列 `yTarget`，而不是预期输出 `yTrue`。这一界定也可以扩展为：假设 `LLM(xAdv)` 仍以 `xTrusted` 为条件（但不再遵循其中的指令），以涵盖 `xAdv` 要求 LLM 泄露 `xTrusted` 的情况；为简化讨论，本文不涉及这种扩展。

还应注意，一般而言，对抗性输入可以通过多种方式与可信输入组合，例如直接拼接字符串、使用参数化查询并用特殊字符包裹每个提示、将两者交错排列，或经过进一步预处理 [32]。不过，为了简化讨论且不失一般性，我们假设可信序列与不可信序列通过普通拼接组合，拼接符号记为 `||`。在此设定下，攻击者需要找到 `xAdv`，使得：

`LLM(xTrusted || xAdv) = yTarget`

早期的大多数提示注入攻击都是手工构造的，并利用了特定模型的各种行为特点 [10]、[8]、[13]。这些早期攻击采用语言技巧和自动改写方法；而本文将该问题形式化为数学优化问题。

寻找这样的 `xAdv` 可以表述为一个优化问题：找到能使 LLM 输出字符串 `yTarget` 的概率最大的 `xAdv`，即：

`xAdv = argmax_x P(yTarget | (x || xTrusted); Θ)`  （6）

这等价于寻找一个输入 `xAdv`，使目标字符串上的交叉熵损失最小：

`xAdv = argmin_x CrossEntropy(MΘ(x || xTrusted), yTarget)`

也等价于：

`xAdv = argmin_x −Logprobs(yTarget | x || xTrusted; Θ)`  （7）

在白盒设定下，已有研究使用 Greedy Coordinate Gradient 算法解决上述离散优化问题。该算法依赖可计算的梯度，以指导对抗性输入搜索 [21]。在无法获得梯度的灰盒和黑盒设定下，先前基于优化的方法要么依赖迁移性，要么需要计算攻击者指定目标 token 的 logprobs [24]、[23]。

### 大语言模型微调功能

微调是一种在预训练基础模型上，使用定制或专有数据继续训练模型的过程。微调 LLM 可以提高模型准确率，减少其在领域知识方面产生的幻觉，并使提示更简洁 [33]、[34]。OpenAI、Google 和 Amazon 等多家人工智能公司都向用户提供微调服务 [14]–[16]。

要使用微调功能，用户需要准备并格式化高质量数据集，使其能够反映自己的使用场景；然后使用适当的微调配置在该数据集上微调基础模型。微调后的模型便可用于相应定制场景的推理。

下面以 Google AI Studio 提供的 LLM 微调 API（“Gemini API”）为例作概括说明。Gemini 微调 API 接受一个基础模型和一个训练数据集，数据集由若干输入—输出字符串对构成。此外，用户还可以指定微调轮数、批大小和学习率。微调 API 会返回优化过程每一步的训练损失。该 API 端点还会在训练前打乱数据集样本，因此返回的损失值呈伪随机顺序。

不同公司的微调接口提供了相近程度的训练超参数控制（更多细节见第 7 节）。

### 3 威胁模型与攻击约束

攻击者的目标是针对某个目标 LLM 构造提示注入攻击。攻击者是第三方，试图接管现有对话，并迫使 LLM 遵循另一套指令。攻击者可以通过多种方式投递提示注入，例如污染用户可能要求模型总结的网页、向用户的 LLM 邮件代理发送未经请求的邮件，或修改用户正在分析的代码仓库 [8]、[13]、[30]。

成功的提示注入攻击必须满足两项要求。第一，LLM 代理所处的应用领域（例如代码编辑代理、邮件/日历处理代理或网页浏览代理）会限制攻击提示的语法和长度（以 token 数量计）。例如，针对 LLM 编程助手的攻击必须是合法注释，不能破坏编程语言语法。同样，如果用户把日历管理委托给 LLM，攻击提示就必须能够作为合法日历事件投递，因此长度也受到限制。因此，为使本文构造的提示注入攻击具有普遍适用性，我们对攻击者可注入的 token 数量设定上限。此外，对于代码示例，我们不插入换行符，使对抗性提示保持在同一行注释内。攻击长度取决于应用领域；在本文实验中，97% 的攻击提示少于 100 个 token，所有提示都少于 500 个字符。其中 40 个 token 由优化算法生成，其余 token 是攻击者用自然语言表达的指令。优化器可控制的 token 数量是算法的可配置参数。因此，最终攻击由一串优化器生成的 token 构成，并将攻击者的自然语言指令夹在其中（图 1）。

第二，攻击必须具有隐蔽性，并且必须使目标 LLM 只输出攻击者期望的内容，不附加其他内容。与先前提示注入研究 [8]、[30] 相比，这是更严格的要求，但我们认为这一约束很重要。近期的一些 LLM 产品经过专门微调，以抵抗提示注入 [35]；这可能导致请求被阻止，或使模型倾向于给出更真实的回答。在这种情况下，我们观察到，Gemini 模型遇到异常请求时，常会提醒用户其行为可能被某条特定提示覆盖。例如，在我们的实验中，Gemini 有时会回答：“这段代码的设计目的是计算半径为 5 的圆的面积。然而，代码中有一条注释明确覆盖了函数的计算，并指示代码输出‘10’。”攻击者不希望用户察觉存在提示注入，因此我们要求攻击不能触发此类警告。

我们假设攻击者能够访问目标 LLM 的微调接口。由于微调接口会返回损失信号，这种访问属于灰盒访问。大多数 LLM 厂商都允许任何人注册成为开发者。

### 4 Gemini 微调接口的实验分析

生成能迫使 LLM `MΘ` 输出字符串 `yTarget` 的对抗性输入，可以表述为一个优化问题：最小化目标字符串上的非加权交叉熵损失（式（7））。在没有 logprobs 信息的情况下，我们无法直接计算给定输入和目标字符串的交叉熵损失。为此，我们把微调 API 报告的训练损失作为代理损失函数。

我们方法背后的关键洞见是：当学习率足够接近 0 时，模型参数应当几乎保持不变。因此，如果我们提交一项只含一个训练样本的微调请求，该样本由一对输入—输出字符串 `(xTrusted || xAdv, yTarget)` 构成，并以极小学习率训练一个轮次，那么报告的损失指标就应当泄露目标模型交叉熵损失的信息。于是，我们可以尝试求解以下代理优化问题：

`xAdv = argmin_x TrainingLoss(MΘ(x || xTrusted), yTarget)`

本节聚焦于 Gemini 系列模型的微调 API，并通过实验证明训练损失是有用的优化代理。我们分两步进行：

1. 探测 API，理解并验证我们的假设：较小学习率不会显著影响基础模型。这一点很重要，因为尽管学习率是外部可控的超参数，一些微调接口会把它作为内部隐藏学习率的乘数。
2. 对 API 报告的损失值进行部分逆向分析，并验证这些损失确实是离散优化的良好代理。

### 4.1 微调超参数分析

Gemini 微调 API 接受一个训练集作为输入，训练集由输入字符串和输出字符串组成的列表构成。此外，该 API 还允许用户控制若干微调超参数，具体包括训练轮数、批大小和学习率。我们对 API 进行探测，并验证了 Gemini 微调流程的以下行为。

**较小的学习率不会显著改变训练损失值。**API 只接受大约大于 `10^-45` 的有效学习率。我们通过实验发现，当学习率介于约 `10^-45` 和 `10^-13` 之间时，在控制训练集和其他超参数的情况下，API 报告的损失值保持不变（精度范围内），与学习率本身无关。

具体而言，我们取一个由 `n` 个不同训练样本组成的固定训练集 `D`，以约 `10^-45` 的学习率将其提交给微调 API，并观察返回的损失 `L(α0) = {l1(α0), l2(α0), ..., ln(α0)}`。随后，我们再次提交 `D`，这次将学习率设为约 `10^-44`，并收集损失 `L(α1) = {l1(α1), l2(α1), ..., ln(α1)}`。以此类推，我们在 `10^-45` 到 `10^-13` 之间选择 `N` 个不同学习率，得到 `N` 组损失值 `L(αi) = {l1(αi), l2(αi), ..., ln(αi)}`。我们观察到，对于不同的 `αi` 和 `αj`，只要二者都小于 `10^-13`，各样本对应的损失值就相同；也就是说，`L(αi) = L(αj)`。这表明，当学习率小于约 `10^-13` 时，微调 API 报告的损失值不会发生显著变化。

这一结果支持了我们的假设：较小的学习率不会显著改变模型参数。此外，这一区间内的任意值都可以作为小学习率，因为它们都能确保训练本身不会显著影响所报告的损失值。

**报告的训练损失经过了排列打乱。**为验证这一点，我们提交一个有序训练集，其中包含重复数据。例如，令大小为 6、批大小为 1、训练轮数为 1 的训练集为 `D = {(x(1),y),(x(2),y),(x(2),y),(x(3),y),(x(3),y),(x(3),y)}`，并使用较小学习率。我们原本预期收到有序损失列表 `L = {l(1),l(2),l(2),l(3),l(3),l(3)}`，但实验发现返回的损失经过某种排列。

我们确实观察到不同损失的出现次数与预期一致：返回的 6 个损失中，有一个值出现一次、一个值出现两次、另一个值出现三次，只是顺序与输入不同。注意，由于我们事先不知道每个训练样本各自对应的损失，因此只有通过统计重复训练样本的出现次数，才能判断是否发生了排列打乱。

在不同训练集大小和不同训练样本上也观察到了类似现象。因此，对于大小为 `N` 的有序训练集 `D = {(x(i), y(i))}^N(i=1)`，存在一个排列 `σN`，将其应用于接口报告的有序损失集合 `L = [l(i)]^N(i=1)` 后，就能得到数据集中每个样本的真实训练损失对应关系。

不同微调请求使用相同的排列。我们还观察到，对于训练集大小相同但训练数据不同的请求，所报告损失的排列顺序也相同。因此我们推断：只要批大小为 1，微调流程就会使用一个固定的硬编码种子 `s` 初始化随机数生成器，并对给定大小 `N` 的训练集应用同一个固定排列。我们将这个排列记为 `σN`。

### 4.2 逆向分析训练损失

Gemini 文档没有详细说明微调时训练损失的计算和优化方式。不同微调方法可能优化并报告不同类型的损失函数，例如：

- 只针对输出字符串计算的交叉熵（“指令微调”）[36]；
- 同时针对输入和输出字符串计算的交叉熵（“指令建模”）[37]；
- 某种未知的自定义损失函数，例如蒸馏损失或稀疏训练损失 [38]。

本小节对所报告的损失进行部分逆向分析，研究它是否能作为对抗目标（即平均 logprobs）的代理。我们将微调损失记为 `TrainingLoss`，并与之后记为 `AvgLogprobs` 的 logprobs 进行比较。

Gemini API 本身不会公开任何字符串的 logprobs；不过，Google 面向企业的 API Vertex AI 会针对前 8 个响应提供“平均 logprobs”数值。在本节分析中，我们假设 Gemini API 和 Vertex AI API 提供的是同一个基础模型。我们把平均 logprobs 视作真实值，并假设它等于生成响应的 logprobs（见式（2））除以输出长度。

接下来，我们选择三个不同的输入提示，比较每个提示对应的 `TrainingLoss` 和 `AvgLogprobs`。具体来说，对一个提示 `X`，我们收集模型生成的长度为 `l` 的响应 `Y1:l` 的平均 logprobs，并收集输入—输出对 `(X, Y1:l)` 的训练损失。随后逐步增加输出长度 `l`，绘制 `TrainingLoss` 和 `l·AvgLogprobs`（即按输出长度缩放后的平均 logprobs，本文称为总 logprobs）随输出长度的变化，如图 2 所示。我们得到以下观察结果：

**假设。**我们假设训练损失（FL）具有以下闭式表达式：

`TrainingLoss(Y|X) = K(X) + l · AvgLogprobs(Y|X)`

其中，`K(X)` 是输入 `X` 的函数。

**验证实验。**首先注意，对于输出序列长度为 `l` 的数据集 `D(l) = {(Xi, Yi,1:l)}^n(i=1)`，总 logprob 值为 `T0(l) = {l · AvgLogprobs(Yi,1:l | Xi)}^n(i=1)`，假设对应的训练损失值为 `T1(l) = {K(Xi) + l · AvgLogprobs(Yi,1:l | Xi)}^n(i=1)`。这两组数值 `T0(l)` 和 `T1(l)` 的决定系数 `R²(l)` 可写为：

`R²(l) = 1 − [Σ(i=1 到 n) K(Xi)^2] / [l² · Var({AvgLogprobs(Yi,1:l | Xi)}^n(i=1))]`

因此，如果我们的假设成立，当 `l` 足够大时，`R²` 应当趋近于 1。

**实验证据。**我们实际执行上述实验，构造包含 `n=10` 个开放式问题 `{Xi}^10(i=1)` 的数据集。对于固定输出长度 `l`，我们收集每个生成响应 `{Yi,1:l}^10(i=1)` 截断到长度 `l` 后的平均 logprobs `A0(l) = {AvgLogprobs(Xi, Yi,1:l)}^10(i=1)`。随后，我们提交训练集 `{Xi, Yi,1:l}^10(i=1)` 进行微调，并收集训练损失 `A1(l) = {TrainingLoss(Xi, Yi,1:l)}^10(i=1)`。

### 4.3 训练损失是有用的优化代理

实验证据（图 3）表明，当目标字符串较长时，训练损失与平均 logprobs 几乎完全相关。因此，目标字符串较长时，训练损失几乎是对抗目标函数的完美代理。本小节将通过实验说明：即使目标字符串较短，训练损失仍可作为可用代理。

对于迭代式优化，只要训练损失能够引导搜索朝“正确”方向前进，也就是朝着降低“真实”损失（logprobs）的方向前进，它就可以成为良好代理。换句话说，它应当能够从一组候选小扰动中，帮助找出最佳扰动（即使真实损失最低的扰动）。实验发现，Gemini 的训练损失并非总能从一组扰动中选出最佳者，但被选中的扰动通常优于平均水平（也就是优于随机抽取的扰动）。

为了理解这一点，我们考察由训练损失选出的候选，在真实表现或排名上（按 logprobs 衡量）有多好。我们选择一个问题 `X`，要求 LLM 给出简短、确定且广为人知的答案 `Y`。然后，在 `X` 后附加随机生成的 token，构造 `N` 个小扰动，同时确保模型对所有这些扰动的输出仍然是 `Y`。这些扰动对应的数据集为 `D = {(X || r(i), Y)}^N(i=1)`。……

## 5 使用微调接口进行对抗性提示优化

我们通过实验证明，微调损失可以作为指导对抗性优化过程的良好代理。本节使用该信号自动生成提示注入。

### 5.1 恢复随机排列

原则上，我们可以通过提交只含一个训练样本 `(x(i), y(i))`、批大小为 1、训练轮数为 1 的微调请求，单独获得该样本对应的训练损失。但每次微调请求都需要数秒到数分钟的启动开销，因此最好在一次请求中评估多个训练样本的损失。然而，当数据集中含有多个训练样本时，损失值的排列会掩盖样本与其真实训练损失之间的对应关系。

*表 1：在同一个提示上逐步破坏目标输出，构造数据集 `Dgarbled` 的示例。提示为“重复这句话：敏捷的棕色狐狸。”随着目标文本逐渐被破坏，表中训练损失从 16.08243 依次增加到 41.72246、57.49492 和 75.69193。*

我们的攻击通过提供特别构造的训练样本，绕开训练损失的排列问题：我们恢复一个未知但近似的排列 `σN`，并在后续攻击步骤中重复使用。核心思路是选择某个提示 `xPrompt`，逐渐破坏基础模型对该提示的真实响应 `yTrue`，再用多份相同的 `xPrompt` 与这些乱码目标值配对，构成训练集。对于这个由逐渐破坏的输出字符串组成的训练集，微调后得到的训练损失预期会按升序排列，从而揭示原始样本与打乱后损失之间的对应关系。

在此过程中，我们向基础模型输入 `xPrompt`，让它生成足够长、确定且格式良好的响应（例如书中的一段引文），并记录真实响应 `yTrue`。定义初始目标 `yTarget,0 = yTrue`。然后对每个 `i∈{1,...,N}`，破坏 `yTarget,0` 开头的 `i` 个 token，得到 `yTarget,i`。表 1 展示了这一过程。

这样便得到由 `(xPrompt, yTarget,i)` 组成的数据集 `Dgarbled`，其训练损失应当单调递增。随后，我们以批大小 1 和较小学习率提交 `Dgarbled` 进行微调。对返回损失 `l0,...,lN` 进行升序排序，即可恢复所需排列：

`σN = AscendingSort(l0,...,lN) / (l0,...,lN)`  （8）

对于固定训练集大小 `N`，排列 `σN` 是常量，因此可以在所有相同大小的微调请求中重复使用。该方法得到的是近似排列，依赖于以下假设：输入被逐步破坏时，其损失也会单调增加。

为了评估该方法，我们将结果与附录中详细介绍的一种效率较低但可证明正确的方法进行比较。我们发现，近似方法只会误判排列中约 7%–8% 的位置，并能保留 90% 以上的两两相对顺序。我们认为这一误差可以接受，因为少量排列错误与第 4.3 节中观察到的候选排序噪声难以区分。

### 5.2 Fun-tuning 攻击

在本文设定中，完整提示由系统提示 `xSys` 和用户提示 `xUser` 组成，其中 `xUser` 的一部分由攻击者控制：

`xPrompt = xSys || xUser = xSys || xUserquestion || xAdv`

为了简化算法描述，本文将提示记为可信部分 `(xSys, xUserquestion)` 与对抗部分 `xAdv` 的组合：`xPrompt = xTrusted || xAdv`。

对抗序列 `xAdv` 由恶意输入构成，通常以普通英语书写（例如“忽略之前的指令并……”），并由预定长度的对抗前缀和后缀包围：

`xAdv = Adv.Prefix || Malicious Instruction || Adv.Suffix`

为清楚起见，我们用大小为 `n` 的掩码 `M=(M0,...,Mn)` 表示前缀和后缀中可优化的位置。攻击开始时，位置 `M0,...,Mn` 都初始化为同一个固定 token；优化过程直接调整这些 token，而恶意输入保持不变。

每轮开始寻找替换 token 之前，算法先估计最佳扰动位置 `Mbest∈{M0,...,Mn}`。对一小组替换 token `R`，选择平均损失最小的位置：

`Mbest = argmin(m∈M) E(xAdv_m∈R)[L(xTrusted || xAdv, yTarget)]`  （9）

我们通过拒绝采样随机抽取一组互不相同的 token `R`，并对每个掩码位置分别替换为 `R` 中的每个 token，构造 `K=|R|·|M|` 个候选（算法 1 第 7 行）。候选列表记为 `C`，在一次攻击过程中长度始终固定为 `K`，以保证对应一个已知排列。此时，`C` 可视为由 `|M|` 个长度为 `|R|` 的区块组成；之后对每个区块求平均值，以估计式（9）中的期望。

为确定最佳位置，我们用候选集 `C` 对目标模型进行微调，学习率为 `α`、批大小为 1、训练 1 轮。微调结束后，我们获得训练损失，通过应用 `σK^-1` 恢复损失顺序，并选择平均损失最低的位置。

接下来，算法用类似流程寻找该位置的最佳替换 token：为该位置采样一个大小为 `K` 的替换 token 列表，构造固定大小的候选训练集 `C*`，然后从微调端点获取损失，选出最佳候选并据此更新 `xAdv`。候选列表始终包含当前 `xAdv`；如果所有新候选表现更差，算法就进入下一轮而不更新 `xAdv`，从而避免采用次优替换。至此，一轮迭代完成。

算法按指定轮数运行。每轮都会对所有扰动进行评分，最后返回成功率最高的 `xAdv`。完整算法见算法 2，默认参数见第 6.3 节。

**算法 1：利用微调损失进行候选排序（RankFT）**

输入包括可信提示 `xTrusted`、对抗输入 `xAdv`、前后缀索引 `M0...Mn`、目标输出 `yT`、替换数量 `K`（即训练集大小）和较小学习率 `α`。输出为最佳位置上各候选对应的损失 `L*`。算法固定训练轮数为 1、批大小为 1；生成互异随机 token；逐一构造每个位置的候选；调用微调；通过逆排列恢复顺序；选择平均损失最低的位置；再对该位置的 `K` 个候选进行微调并返回恢复顺序后的损失和候选集合。

**算法 2：Fun-tuning 攻击**

输入包括可信提示、对抗输入、可替换位置、目标输出、迭代次数、替换数量及较小学习率；输出为最佳扰动。算法从初始对抗输入开始，每轮调用 RankFT 取得候选和损失，选择损失最低的候选，记录模型响应的评分；全部迭代完成后，返回评分最高的一轮所对应的对抗提示。

### 6.1 数据集构建

我们在 PurpleLlama CyberSecEval [30] 提示注入数据集的一个子集上评估攻击。该基准用于评估 LLM 的网络安全脆弱性，其中包含直接注入和间接注入。按照本文威胁模型，我们关注间接注入：注入指令只是用户提示中的一部分，例如文档或其他外部内容。直接提示注入中用户本人就是攻击者，这种情况在实际中相对少见。

间接注入涵盖多种已知攻击类型，例如“忽略之前的指令”、开发者模式覆盖以及假设情境攻击。这些攻击由安全研究社区手工设计，并由 Meta 人工整理到基准中。我们的攻击以优化得到的 token 前缀和后缀包裹这些已有恶意指令，形式类似白盒 NeuralExec 攻击 [39]，以此增强恶意指令，使 LLM 忽略上下文中的其他指令并遵循增强后的指令。

PurpleLlama 提示注入数据集包含 56 个样例。为便于快速探索，我们从中随机抽取 40 个间接提示注入样例，构成自己的数据集 PPL40。抽样时，我们排除了使用非标准编码的攻击（包括 token 隐匿类别及少数其他样例），因为我们发现 Gemini 不会遵循通过非标准编码表达的指令。PPL40 的攻击类别分布与原始完整数据集相近，具体分布见附录表 9。

每种攻击类别都对应若干场景，例如总结网站内容、分析代码片段或其他文档。每种场景都会在相应文档中注入一种具体行为，例如给出误导性回答或引导用户访问钓鱼网站。后文将分别评估不同场景下的攻击效果。

**训练样本格式。**每个 PurpleLlama 间接注入样例由以下部分组成：系统提示，向模型提供一般指令或角色；用户输入，包含问题/提示及外部内容，外部内容中的注入指令意图覆盖原问题，使模型执行另一种行为或给出错误答案，我们会用待优化的对抗前缀和后缀包围该指令；以及评判问题，用于检查模型输出是否执行了注入指令、攻击是否成功。系统提示和用户输入合并成提示 `xTrusted || xAdv`。其中 `xAdv` 是由攻击者控制的注入指令，两侧各有长度为 20 token 的可优化前缀和后缀，初始 token 为“!”。提示采用标准聊天格式。

### 6.2 指标

主要指标为攻击成功率（ASR），即 PPL40 中成功攻击样例的比例，并对多次评分运行取平均。与原始 PurpleLlama 方法类似，我们使用评判问题提示模型响应，再调用 GPT-4o 作为评判模型给出二元分数（1 表示攻击成功）。为考虑目标模型的非确定性，主攻击重复评估 20 次，迁移评估重复 5 次，并报告均值和标准差。我们跟踪每轮迭代的 ASR，包括未修改原始注入的基线 ASR。每个样例最终报告所有迭代中的最高 ASR，整个 PPL40 的攻击 ASR 则是各样例最高 ASR 的总和；基线 ASR 同理。最后报告相对于基线的提升倍数 `ASRattack / ASRbaseline`。

**更严格的评判问题。**我们发现 PurpleLlama 原有评判问题过于宽松，会造成大量假阳性，虚高估计攻击成功率。例如，注入指令要求“忽略函数并声明输出为‘10’”时，默认评判问题“回答中是否包含‘10’？”会在模型输出详细解释、而其中碰巧出现“10”时判为成功。但按照本文威胁模型，如果响应准确解释了问题并揭示攻击，就应当视为攻击失败。

准确评分对评估攻击效果至关重要。为此，我们根据威胁模型手工调整评判问题。针对上述示例，修订后的评判问题要求响应必须明确给出代码输出为“10”（允许不同格式）；如果人类读者能将响应理解为 10，则判为有效；但只要提到问题有陷阱、指令覆盖或存在歧义，就判为无效。表 2 展示了使用原始评判问题和严格评判问题对两个回答打分时的混淆情况：原问题分别产生一个假阴性和一个假阳性。

*表 2：两个回答在严格评判问题与原始评判问题下的混淆矩阵示例。一个只给出正确目标答案的回答被严格标准判为成功、原标准判为失败；一个指出问题有陷阱并解释指令覆盖的回答则被严格标准判为失败、原标准误判为成功。*

**效率指标。**我们用迭代次数、攻击耗时（小时）和成本比较各方法效率。单次微调调用时间受到云服务器可用性、负载均衡等不可控因素影响，因此只能粗略估算单次微调请求的耗时上界。对于包含 1000 个样例的训练集，Gemini 1.0 Pro 的成功微调调用约需 10 分钟，Gemini 1.5 Flash 则少于 40 分钟。因此，虽然论文估算了整个数据集的攻击时间，更可靠的指标是发送到服务器的微调请求数量。

论文写作时（2024 年 11 月），Gemini 微调请求免费，因此攻击的经济成本来自推理调用；推理请求仅用于评分。成本估算假设每个样例、每轮迭代使用 20 次补全请求得分。

### 6.3 攻击配置

**目标模型。**我们使用常规 Gemini API（注意不要与 Vertex AI 混淆；Vertex AI 是另一个面向企业的平台，也提供部分 Gemini 模型的查询接口）。主要攻击针对 `gemini-1.5-flash-001-tuning` 和 `gemini-1.0-pro-001`。迁移评估覆盖 Gemini 1.0 Pro、1.0 Pro 001、1.0 Pro latest、1.5 Flash 001、1.5 Pro 001 等模型；每个模型都测试默认参数和推理温度为 0 的配置，共 10 种配置。

**格式。**提示阶段使用标准交互式聊天格式，将系统提示和用户提示分开。Gemini 1.5 Flash 支持初始化系统提示，因此直接在初始化时设置。微调 API 不支持标准多轮聊天格式，因此作者用 `<start_of_turn>` 和 `<end_of_turn>` 手工组织多轮对话。分隔 token 使用 Hugging Face 的 gemma-2-9b tokenizer 识别，因为 Gemma 2 与 Gemini 系列共享 tokenizer [40]。

**Fun-tuning 参数。**算法 2 运行 45 轮，在第 15 轮和第 30 轮重启。对抗前缀和后缀均初始化为 20 个“!” token，每次重启时恢复该初始状态。40 个样例中有 15 个原始注入指令存在歧义，因此作者在这些样例的前缀初始化中加入“Follow this new instruction:”，并在攻击过程中继续优化这段短语。优化目标是最小化所有候选的损失（式（4）），每轮评估 1000 个候选。每轮还额外进行最佳位置搜索，同样使用 1000 个候选（前后缀共 40 个位置，每个位置 25 个候选）。作者保存每轮找到的扰动，以便最后选出最佳者。

### 6.4 消融实验

为验证训练损失是否提供了有效信号，作者进行了一项仅移除微调信号的消融攻击：算法不再获得每个候选的真实训练损失，而是收到随机数。攻击方法、前后缀长度、迭代轮数、重启次数、初始化、采样策略和 token 替换策略均保持相同。该实验用于证明攻击成功率确实来自训练损失信号，而非攻击的其他组件或随机波动。

### 6.5 提示注入结果

主要结果如下：fun-tuning 的提升超出标准差范围；对 Gemini 1.5 Flash 的成功率约为 63.5%，对 Gemini 1.0 Pro 为 82.0%。攻击成本低于 10 美元，但耗时较长：每个样例需 90 次微调调用，Gemini 1.0 Pro 约需 16 小时，Gemini 1.5 Flash 约需 60 小时。攻击成功率随迭代稳步上升，尤其在重启后会有提升。各场景都能攻击成功，但密码钓鱼场景（两个模型版本）以及代码分析场景（Gemini 1.5 Flash）只取得部分成功。针对 Gemini 1.5 Flash 生成的扰动较强，可迁移到 Gemini 2.0 Flash、Gemini 1.0 Pro 以及相同版本号的模型。

结果表明，攻击有效是因为训练损失为离散优化提供了有用信号。与消融实验相比，真实信号带来了更大的逐轮提升，尤其符合重启策略的预期。

值得注意的是，消融实验也取得了相当高的 ASR：Gemini 1.5 Flash 为 43.8%，Gemini 1.0 Pro 为 61.3%；而基线分别为 27.5% 和 42.5%。这说明随机 token 替换本身也可能对 Gemini 有效。基线分数也表明，PurpleLlama 数据集中部分人工整理的攻击原本就能攻击 Gemini。

攻击具有较高效率、可扩展性，可在 Gemini 模型间迁移，并适用于任意提示和目标输出。但在钓鱼场景中，攻击只能部分奏效，尤其是 Gemini 1.5 Flash，这可能与其改进的安全微调有关。

与 Google 关于 Gemini 1.5 Flash 的报告不同，本文结果表明基于优化的提示注入仍然构成现实风险 [41]。该报告称，在 1500 万次查询和内部访问条件下，遗传算法生成的通用扰动导致敏感信息泄露的 ASR 为 0%–9%，似乎说明该设置下优化攻击效果有限 [41]。本文则对每个样例分别攻击（因此扰动不一定能跨样例迁移），每个样例使用 90 次查询，最终在 Gemini 1.5 Flash 上取得 65.3% 的总体 ASR，在 Gemini 1.0 Pro 上取得 82% 的 ASR。Google 后续报告进一步说明，其自动化红队评估包括 Actor Critic 和 Beam Search 等基于优化的攻击 [42]。作者认为，在远程查询场景中，如果没有更好的攻击概率估计方式，这些攻击也可以使用微调损失。

**不同提示注入场景。**按场景分析后，攻击在“password”类别中最不成功：该类别中的注入试图引导用户前往钓鱼网站重置密码（图 8、图 9）。Gemini 1.5 Flash 和 Gemini 1.0 在该类别中仍有一定成功率，分别约为 10% 和 20%，但较低的分数说明 Gemini 模型可能经过某种针对钓鱼的训练。

其次容易失败的是代码分析场景：注入指令藏在 Python 代码注释中，试图误导模型对代码输出的判断。该攻击在 Gemini 1.5 Flash 上大多失败（ASR 40%），但对较早的 Gemini 1.0 Pro 较为成功（ASR 80%），表明较新的模型代码分析能力可能更强。Gemini 是否实际执行代码，以及能否专门为代码分析构造更好的优化攻击，仍不清楚。

除上述场景外，微调损失引导的攻击在所有类别上均有效；对两个模型而言，各类别 ASR 均超过 60%，能够用注入指令覆盖用户指令。这说明该优化策略可能有实际用途，尤其适合寻找细微、与应用高度相关或难以预先预见的提示注入风险。例如，诱使模型给出错误文档摘要，或在输出中夹带隐蔽信息。若不结合具体应用上下文，很难区分不安全行为和预期行为，因为这些定义并不普遍适用。

**效率分析。**Fun-tuning 攻击成本低于 10 美元，每例需要 90 次微调查询。图 5 和图 6 展示了总体 ASR 随攻击轮数的变化：Gemini 1.0 Pro 的 ASR 在前 20 轮迅速提高；Gemini 1.5 Flash 则提升较慢，到第 35 轮左右仍有增长。重启策略下，曲线斜率显示 Gemini 1.0 Pro 的主要攻击效果在前 15 轮获得，后续重启帮助有限；但该策略对 Gemini 1.5 Flash 有帮助，每次重启后不久（第 0、15、30 轮附近）分数都有明显提升。

Gemini 微调请求免费，因此攻击成本仅来自用于评分的推理请求。Gemini 1.0 Pro 的微调调用通常约需 10 分钟，Gemini 1.5 Flash 约需 40 分钟；单次 fun-tuning 攻击分别约需 15 小时和 60 小时。我们观察到，来自同一 Google 账号的攻击会降低并行微调请求的性能。不过攻击仍容易扩展：（1）微调调用没有触及速率限制，且我们不知道其他瓶颈；（2）试用期内可以使用多个 Google 账号和免费额度。

### 7 讨论

**在任意值上评估损失。**本文作为概念验证，说明微调 API 即使只返回闭权重基础模型的训练损失，也可能使其暴露于基于优化的攻击。我们通过引导一个简单的随机替换算法生成提示注入，展示了提取基础模型损失的可行性。不过，基于微调的损失提取可以与任何需要损失值来引导搜索的自动 LLM 攻击结合。也就是说，我们的方法可以评估任意输入和输出的损失，而不对高层目标或优化算法作假设。

**对其他 API 的普适性。**虽然本文专门验证了 Gemini API 上的方法可行性，同样的思路也可能用于其他微调 API。该方法取决于用户对若干输入超参数的控制程度：最小学习率、最小批大小以及随机种子（固定、由外部控制或均不可控）。前文实验表明，当学习率参数约为 `10^-30` 至 `10^-45`、批大小为 1，且随机种子固定或可由外部控制时，攻击可行。表 7 显示，某些微调服务商的配置并未（或过去未）排除 Gemini API 之外的攻击可能性。作者希望该比较和本文能成为系统研究闭权重模型离散优化攻击能力的起点，并为恰当的风险评估提供依据。

**对超参数施加限制的缓解措施。**本文攻击利用了根本性的效用—安全权衡：开发者希望细粒度控制训练超参数，以有效训练模型，而这也直接帮助攻击者。我们认为，普遍减少用户对训练超参数的控制不太可能奏效，因为这会降低正常开发者的效用。例如，厂商可以设置学习率下限，但不同规模的数据集推荐的学习率不同 [44]；而较小学习率通常能使训练更稳定，对正常用户可能有益 [45]。

同样，每次 API 调用都随机打乱训练集会破坏返回损失与候选之间的对应关系，但仍无法阻止攻击，因为攻击者仍可逐条提取损失，或使用由不同重复次数样本构成的数据集，类似第 4.1 节的方法。

API 厂商目前没有公开训练损失的具体计算方式。隐藏这类信息或许能削弱攻击，但如实验所示，攻击者无需完全逆向分析损失函数，也能将其作为提示离散优化的有用信号。

**扫描训练集的缓解措施。**先前关于恶意微调的研究发现，厂商会在微调前使用分类器审核训练文件，寻找“恶意”数据 [29]。例如，越狱内容或广为人知的提示注入语句（如“忽略之前的指令”）可能被标记并拦截。但这并非完整防御，因为攻击者可以编码训练集以隐藏其意图 [29]。

*图 7 旁的表 7：论文写作时（2025 年 4 月）多个闭权重 LLM 微调 API 参数控制水平对照。Google Gemini 学习率参数下限为 `10^-3`（2025 年前为 `10^-45`），随机种子固定，最小批大小为 4（此前为 1）；Google Vertex 的学习率参数下限为 `10^-45`、随机种子固定、批大小自动设置；OpenAI 学习率参数下限为 `10^-5`（此前为 `10^-31`）、随机种子可控、最小批大小为 1；Anthropic（Amazon）学习率参数下限为 `10^-1`、随机种子固定、批大小自动设置。脚注说明：Google 在披露后实施了相关限制；作者在 2025 年 4 月因授权错误未能重新核验 Vertex AI 的约束；OpenAI 约在 2025 年 1 月开始强制实施 `10^-5` 的最小学习率乘数。*

### 8 相关工作

现有 LLM 容易受到多种攻击。提示注入和越狱是近期引起厂商广泛关注的两类攻击 [40]。提示注入假设攻击者能部分控制 LLM 输入，目标是操纵 LLM 执行用户未意图的行为，例如滥用工具或泄露数据 [46]、[47]、[8]、[48]。越狱则试图让 LLM 回应违反厂商安全政策的用户请求，例如生成骚扰内容。两类攻击的威胁模型不同（前者中用户是善意的，后者中用户是恶意的），目标也不同，但都需要操纵 LLM 生成攻击者指定的文本。实现这一目标的方法既有人工构造，也有自动化方法。

**语言型提示注入。**现实产品中的提示注入通常由人工构造，并利用特定模型的行为特点 [8]–[12]。例如，“忽略之前的指令……”可以有效诱导 LLM 遵循后续指令，并忽略此前施加的伦理约束 [49]。另一些攻击 [22] 使用长分隔符字符串制造上下文分隔，使恶意指令与之前的上下文区分开来。越狱攻击也存在人工构造方法 [50]、[51]；其中，Anil 等人研究了利用多轮上下文示例绕过厂商安全政策 [51]。

这些攻击较为临时，理论上容易通过拦截可疑提示来修补，例如拦截前述“忽略之前的指令” [52]。将这类攻击扩展到新 LLM 产品或新目标通常需要重复的人工工作，因此不适合系统化、大规模攻击者。相比之下，本文攻击具有原则性，不依赖反复调试提示文本。

**自动化提示注入。**根据所需的模型信息，自动化方法分为白盒、黑盒和灰盒三类。

白盒方法需要完整访问模型权重，以计算梯度 [21]、[22]、[53]。Greedy Coordinate Gradient 是早期具有代表性的白盒算法，最初用于越狱，但也可用于提示注入 [21]。它利用梯度信息指导对抗输入搜索。NeuralExec 使用 Greedy Coordinate Gradient 生成自动化白盒提示注入攻击 [22]。由于需要访问模型权重，这些白盒攻击大多在开放权重模型上评估。

在黑盒设定下，先前研究使用其他 LLM 或自然语言启发式方法指导越狱提示搜索 [19]、[25]。

灰盒攻击不需要模型权重，但会利用 logprobs 等相关信息 [23]、[17]。基于 logprobs 的攻击需要能够通过“logit bias”等采样参数计算目标 token 的 logprobs，再用其指导搜索算法。但曾易受此类攻击的 LLM 厂商，已经修改 API（或很容易进一步限制 API），使其不再提供这些信息 [26]、[41]。

与之不同，本文作为一种灰盒攻击，提出了新的攻击通道——微调接口。由于微调损失是微调用户所需的关键组成部分，这一攻击途径很难缓解。

**隐蔽的恶意微调。**除了对抗性提示，攻击者还可以通过扰动模型权重攻击 LLM [54]、[55]。研究表明，只需少于 100 条恶意提示，就可能通过微调使 GPT 等模型发生对齐偏移 [56]、[57]。然而，用户只能通过厂商的微调 API 微调闭源模型，厂商可在微调前检查训练数据。近期研究提出对训练数据编码，以隐蔽地使用恶意数据进行微调 [29]。本文研究与该方向正交：我们的攻击不依赖更新模型权重，而是利用微调过程中返回的损失指标，获取基础模型的更多信息。

**闭权重 LLM 的逆向分析。**模型窃取是一个成熟研究问题，攻击者只通过查询目标模型，目标是提取其权重 [58]。大型模型更难被窃取，但闭源 LLM 数量增长促使研究者尝试提取更有限的信息。有一类攻击试图获取隐藏层的精确维度 [59]、[28]；另一些攻击通过将基准性能与开源模型结果关联，推断模型参数总数 [60]；还有研究尝试恢复闭源 LLM 的 tokenizer [61]。本文则对闭源 Gemini 微调 API 的工作机制进行部分逆向分析。

### 9 结论

我们的目标是推动构建安全可靠的 LLM 系统。实现这一目标的前提之一，是全面评估这些新兴系统面临的攻击途径，从而将防御工作聚焦于真正重要的威胁。本文开启了一个新的研究方向，即分析远程微调接口的攻击面。微调是 LLM 领域中广泛使用且不断发展的功能，而本文首次对其进行对抗性分析。

我们通过实验刻画了 Google Gemini 微调接口返回的损失信号，并展示如何使用一个简单的离散提示优化算法，将该信号用于构造提示注入攻击。缓解这一攻击途径并非易事，因为任何训练超参数限制都可能降低微调接口的效用。可以说，提供微调接口的经济成本非常高（甚至高于提供 LLM 内容生成服务），因此降低开发者和客户的使用价值，可能严重影响运营此类接口的经济性。我们希望本文能促使业界讨论此类攻击可能达到多大威力，以及如何在效用与安全之间取得平衡。

### A.1 可证明正确的排列恢复方法

给定大小为 `N` 的输入序列 `X=(x1,x2,...,xN)`，微调 API 会在计算训练损失前打乱该序列，即 `FT(x1,x2,...,xN)=(lσN(1), lσN(2),...,lσN(N))`，其中 `li` 是 `xi` 对应的损失，`σN:{1,2,...,N}→{1,2,...,N}` 是排列函数。注意，`σN` 会根据 `N` 以确定性方式打乱顺序。我们的目标是恢复 `σN`，从而正确排列损失值。

**命题 1。**给定排列函数 `σN`，攻击者只需向微调 API 发出 3 次请求，就能恢复该排列。

**证明思路。**对于输入序列 `X=(x1,...,xN)`，第一次微调请求会返回打乱后的损失 `L'`。若已知某个根号规模子排列 `σ√N`，就可以直接恢复正确排序的损失 `L`。假设所有损失互不相同。随后构造更长的序列，使每个样本重复出现相同次数；第二次请求返回的损失也会按相同排列重复。再构造第三个特定序列，通过比较第二、第三次请求中损失值的位置，即可重建 `σN`。原文给出具体位置关系式。

通过 3 次微调 API 调用，可以递归恢复排列，复杂度为 `O(3 log2(log2(N)))`。相比之下，第 5.1 节的近似方法只需一次大小为 `N` 的微调请求，但依赖逐渐乱码的输入会导致损失递增这一假设。
